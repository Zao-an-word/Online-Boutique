### 第 1 页 — 问题定义与研究背景

**标题**：OmniAnomaly 算法复现——问题定义

**核心内容**：
- **任务**：多元时间序列异常检测
- **场景**：Online Boutique 微服务系统，11 个服务的 CPU + Memory 指标
- **输入**：22 维时间序列（11 服务 × {cpu, mem}），每 30 秒一个采样点
- **输出**：每个时间窗口的异常分数 + 阈值判定（正常/异常）
- **故障类型**：CPU Stress、Network Delay、Pod Kill

**口述要点**：
> 我们的目标是在真实的 Kubernetes 微服务环境中，复现并验证 OmniAnomaly 算法对运维故障的检测能力。选取 3 种典型故障 × 3 个关键服务共 9 组实验，覆盖了容器环境中最高频的异常场景。

### 第 2 页 — OmniAnomaly 核心思想

**标题**：从重建误差到重建概率

**核心概念**：一张图对比两种范式

```
传统方法（重建误差）：
  x → Encoder → z → Decoder → x̂
  异常判定: MSE(x, x̂) > 阈值  ← 阈值难统一

OmniAnomaly（重建概率）：
  x → Encoder → q(z|x) → Decoder → p(x|z)
  异常判定: log p(x|z) < 阈值  ← 概率天然可比
```

**为什么重建概率更好**：
1. 概率值在不同维度间可直接比较，不需要维度级标准化
2. 不仅考虑重建值本身，还考虑了重建的不确定性（方差）
3. 训练时模型学会的是"正常数据的分布"，异常数据自然落在低概率区域

**口述要点**：
> OmniAnomaly 的核心创新在于用重建概率替代传统方法的重建误差。想象一下——模型在训练阶段只见过正常数据，它在隐空间中学会了正常数据的"形状"。当异常数据进来时，模型试图用正常的"形状"去解释它，结果自然是概率极低——这就是检测的依据。

**配图建议**：编码器→隐空间→解码器的简化流程图，标注"重建概率"输出

### 第 3 页 — 四大核心组件

**标题**：OmniAnomaly 模型架构

| 组件 | 作用 | 为什么需要它 | 本实验配置 |
|------|------|-------------|:---:|
| **GRU 循环网络** | 对时间窗口内序列建模，捕捉时序依赖 | 指标不是独立的——CPU 飙高后通常会伴随内存变化，GRU 捕捉这种先后关系 | `rnn_num_hidden=128` |
| **VAE 变分自编码器** | 学习正常数据的隐空间分布，用概率建模替代点估计 | 传统自编码器只输出一个确定性的重建值；VAE 输出一个分布，能表达"这个点有多不确定" | `z_dim=6` |
| **Planar Normalizing Flow** | 对 VAE 的隐变量后验分布做 10 层可逆变换 | 标准 VAE 假设后验是高斯分布——太简单了。NF 把简单的高斯"揉"成任意形状，更贴近真实数据 | `nf_layers=10` |
| **Linear Gaussian SSM** | 对隐变量 z 的时间演化建模 | 标准 VAE 假设各时间步的 z_t 独立，但真实系统的状态是连续演化的。LGSSM 建模 z_t = z_{t-1} + ε_t | 启用 |

**口述要点**：
> 这四个组件形成了一条完整的 pipeline——GRU 负责"看懂时间"，VAE 负责"学会正常"，NF 负责"表达灵活"，LGSSM 负责"连接前后"。每删掉一个都会掉效果，它们之间是互补关系。具体哪个组件贡献多大，论文里有消融实验，我今天重点讲复现。

### 第 4 页 — 实验环境与数据采集管线

**标题**：实验环境搭建与数据采集

**环境配置**：

| 组件 | 配置 |
|------|------|
| Kubernetes | Minikube（CPU=4, Memory=8192MB） |
| 微服务 | Online Boutique 11 个微服务（namespace: `boutique`） |
| 负载生成 | Locust（`loadgenerator`），持续模拟用户购物流程 |
| 监控 | Prometheus（namespace: `monitoring`） |
| 故障注入 | ChaosMesh（namespace: `chaos-testing`） |
| 算法环境 | Python 3.6 + TensorFlow 1.12.0 (conda env `omnianomaly`) |

**数据采集管线**：

```
正常数据采集（6 小时）         故障注入（9 组，~2 小时）       数据转换 + 训练
─────────────────────        ─────────────────────        ──────────────
Prometheus 端口转发           ChaosMesh 注入故障            长表 → 宽表 pivot
↓                             ↓                            Pod 名聚合为服务名
collect_metrics.py            run_fault.ps1                 生成异常标签
--duration 360                -Type cpu/delay/kill          ↓
--interval 30                 -Service frontend/           训练/测试集分割
--metrics cpu_rate             cart/productcatalog          ↓
  memory_working_set          ↓                            输出 .pkl
↓                             自动记录起止时间               送入 OmniAnomaly
normal_train.csv              9 组 fault_*.csv
(637 有效行 × 22 维)          + 时间窗口日志
```

**故障实验矩阵（3 类型 × 3 服务 = 9 组）**：

| 故障类型 | ChaosMesh 资源 | 目标服务 | 参数 |
|----------|---------------|----------|------|
| CPU Stress | StressChaos | frontend, cartservice, productcatalogservice | 2 核, 80% |
| Network Delay | NetworkChaos | frontend, cartservice, productcatalogservice | 500ms + 100ms jitter |
| Pod Kill | PodChaos | frontend, cartservice, productcatalogservice | pod-kill action |

**口述要点**：
> 数据是这个实验最耗时的部分。正常数据要采集 6 小时保证覆盖业务的自然波动，9 组故障实验要精确记录起止时间——因为 POT 算法和标签生成都依赖秒级精度。整个采集管线我们用 PowerShell 脚本自动化了，但故障注入和正常采集绝对不能同时跑，否则训练数据被污染，模型学到的是"有故障才算正常"。

### 第 5 页 — 9 组实验总览（最核心页）

**标题**：9 组对照实验——从 F1=0.112 到 F1=0.786

**配图**：`images/fig1_experiments_comparison.png`（全页展示）

**9 组实验演进路径**：

```
阶段一：特征探索（#1–#5）
  #1 Baseline (F1=0.112)
    │ 全量 494 维 + 全命名空间 → 几乎无法区分正常/异常
    │
    ▼
  #3 强故障 (F1=0.553, +392%)
    │ 关键转折！故障强度比特征工程更重要
    │ 2 核 CPU + 512MB 内存压力
    │
    ▼
  #5 精选特征 (F1=0.589, +6%)
    │ 第二个转折！首次出现 TN=562
    │ 模型终于学会区分"这是正常的"

阶段二：数据源验证（#6–#8）
  #6 GDN 数据 (F1=0.968)
    │ 人造理想数据天花板
    │ 正常段几乎无波动，故障信号瞬时
    │
  #7/#8 回到原始数据 (F1≈0.48)
      数据源本身质量是根本瓶颈

阶段三：重新采集 + 调参（#9）
  #9 新管线 (F1=0.786)
    6h 正常 + 9 组单服务故障 + 22 维精选
    w30 窗口 + 完整调参
```

**三个关键数字**（口述时强调）：

| 对比 | F1 变化 | 启示 |
|------|:---:|------|
| #1→#3 | 0.112 → 0.553 (+392%) | 故障强度比特征工程重要 |
| #5→#6 | 0.589 → 0.968 (+64%) | 数据质量决定天花板 |
| #1→#9 | 0.112 → 0.786 (+602%) | 整体优化路径有效 |

**口述要点**：
> 这张图是整个实验的核心。我们从左上角 0.112 做起，当时 494 维全量指标，模型几乎把每个正常点都判为异常——FP 有 1298 个。第一个关键转折在 #3，把故障从 1 核提到 2 核后，F1 翻了 5 倍。第二个转折在 #6，换成 GDN 的实验设计数据后直接飙到 0.968，但这数据太"干净"了，正常段几乎是一条直线。最后我们用真实重新采集的数据，配合完整的调参，在实验 #9 达到了 0.786——这才是真实场景下有参考意义的结果。

### 第 6 页 — 特征维度与检测效果的关系

**标题**：降维——F1 提升 7 倍的关键

**配图**：`images/fig2_dimension_vs_f1.png`（全页展示）

**核心发现**：

| 维度区间 | 实验 | F1 范围 | 说明 |
|----------|------|:---:|------|
| 精选区（22-54 维） | #6, #8, #9 | 0.472–0.968 | 仅保留 boutique 命名空间的 cpu/mem 指标 |
| 过渡区（156-234 维） | #2, #3, #4 | 0.109–0.553 | 包含更多命名空间和指标类型 |
| 原始区（494 维） | #1 | 0.112 | 所有命名空间、所有 Prometheus 指标 |

**为什么维度越高效果越差**：
1. **低方差噪声**：494 维中 92.6% 的列在训练集中方差为零或极低，这些不是特征，是噪声
2. **语义无关**：`kube-system`、`monitoring` 等命名空间的指标与 boutique 业务无关
3. **VAE 容量稀释**：z_dim=6 的隐空间要同时编码 494 维信息，有效信号被淹没

**口述要点**：
> 降维是我们最大的意外收获。从 494 维到 22 维，F1 提升了 7 倍。不是算法不够好，而是我们喂了太多噪声。最终的精简方案特别简单：只取 boutique 命名空间，只取 cpu 和 memory 两个指标，11 个服务就是 22 维。人工精选的 22 维远超自动方差筛选的 36 维和语义去噪的 54 维——因为自动方法不知道哪些维度在语义上属于同一个监控对象。

### 第 7 页 — 异常分数分布与时序分析

**标题**：实验 #9 检测效果可视化

**配图**：上方 `fig3_score_distribution.png`，下方 `fig4_score_timeline.png`（上下排列）

**分布图解读**：
- 正常窗口：异常分数集中在低值区（均值约 -10），分布较集中
- 异常窗口：异常分数明显右移（均值约 +5），且方差更大
- Cohen's d 分离度：衡量两组分布的可分性

**时序图解读**：
- X 轴：测试窗口序号（时间推进）
- Y 轴：异常分数（越高越异常）
- 红色背景：真实故障注入时段（attack=1）
- 绿色圆点：正常窗口 | 红色三角：异常窗口
- 黄色虚线：Best-F1 阈值（=8.0）

**观察要点**：
1. 故障注入开始后，异常分数迅速攀升——模型对故障有实时响应
2. 故障清除后，分数逐步回落——模型能感知系统恢复正常
3. 部分正常窗口的分数也较高——体现了真实数据中的自然波动噪声

**口述要点**：
> 这是一个非常直观的验证。红色背景是我们的故障注入时段，可以看到每次注入后，异常分数——也就是图中的红三角——会立刻跳起来。故障清除后恢复正常。但也要诚实地说，和 GDN 数据相比，真实数据的正常段有更多自然波动，这也是 F1 从 0.968 降到 0.786 的根本原因——真实系统的正常行为本身就是有噪声的。

### 第 8 页 — 超参数敏感性分析

**标题**：窗口长度——论文默认值 vs 真实场景最优值

**配图**：`images/fig5_window_sweep.png`（全页展示）

**窗口长度搜索（实验 #9 子实验）**：

| 窗口长度 | F1 | 说明 |
|:---:|:---:|------|
| w5 | 0.600 | 论文默认值，在真实数据上效果最差 |
| w10 | 0.616 | |
| w20 | 0.643 | |
| w28 | 0.692 | |
| **w30** | **0.786** | ★ 真实数据最优 |
| w40 | 0.762 | 过大窗口开始丢失局部信息 |

**关键发现**：
- 论文的 w5 在真实数据上比最优 w30 低 18.6 个百分点
- 原因：论文数据集的故障是瞬时突变，短窗口即可捕捉；真实微服务的故障是渐进累积的（CPU 逐步升高、延迟逐步增大），需要更大窗口
- **POT 算法完全失效**：level=0.01 时 TP=0（将所有点判为正常），level 调大一档则 FP 爆炸。最终 F1 依赖 Best-F1 搜索（需真实标签）

**口述要点**：
> 论文默认的窗口长度是 5，但在我们真实采集的数据上，w5 的 F1 只有 0.600，w30 则是 0.786——差了将近 19 个百分点。这是因为论文用的是大型工业数据集，故障往往是瞬时突变。但在我们的微服务环境中，CPU 压力是渐进升高的、网络延迟是逐渐累积的——你需要一个足够大的窗口来捕捉这个"累积偏差"。这也提醒我们，论文复现不能直接照搬超参数。

### 第 9 页 — 核心结论与局限性

**标题**：复现结论与局限讨论

**四个核心发现**：

| # | 发现 | 证据 | 启示 |
|:---:|------|------|------|
| 1 | **数据质量 > 模型调参** | F1 从 0.112→0.786，最大的三次跳升分别来自增强故障、换用高质量数据、重新采集调参 | 花 80% 精力在数据上 |
| 2 | **降维是关键杠杆** | 494 维 (0.112) → 22 维 (0.786)，F1 提升 7 倍 | 人工精选 > 自动筛选 |
| 3 | **故障强度至关重要** | 1 核故障 (0.112) → 2 核故障 (0.553)，F1 提升 5 倍 | 弱信号检测仍是难题 |
| 4 | **POT 在小样本不可靠** | 637 行数据上 POT F1=0，完全失效 | 需要更大数据集或替代方法 |

**局限性**：

| 局限 | 说明 |
|------|------|
| 训练集规模 | 仅 637 行（~6 小时），远少于论文的数万条样本 |
| 特征类型 | 仅 cpu/mem，缺少网络 I/O、磁盘、应用级指标 |
| 故障覆盖 | 仅 3 种故障类型，未涵盖内存泄漏、级联故障等 |
| 单故障假设 | 每次仅注入一个服务故障，生产环境常为多故障并发 |
| POT 失效 | 小样本上完全无法自动确定阈值 |
| 框架依赖 | TensorFlow 1.x（EOL），迁移成本高 |

**口述要点**：
> 最后总结四点。第一，数据质量决定了天花板——我们花了 8 组实验才走到 0.786。第二，降维是最廉价的提升手段——从 494 列删到 22 列不需要任何算法改动。第三，故障强度——弱故障连人都看不出来，不能指望算法能检测。第四，POT 在几百行数据上就是不可靠的，这是论文方法的已知局限，不是我们的问题。
>
> 坦诚地说，0.786 的 F1 在真实场景下只是一个起点。后续要做的事情很多：采集更多数据、接入更多指标类型、升级到 TF2/PyTorch、以及最重要的——把这个模型真正接入 AIOps Agent 的 LangGraph 诊断管道中。
